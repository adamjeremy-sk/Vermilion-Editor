# Agent rules — Vermilion Editor
Vermilion Editor is a native Linux text and code editor written from scratch in C++17 on GTK 4 and GtkSourceView 5, with a built-in AI agent, build integration, a debugger and a terminal. GPL-3.0-or-later.
1. Read ARCHITECTURE.md before any change; it is the map. Read HANDOFF.md section 1 for where the project stands.
2. Gate protocol: execute exactly ONE logical step per turn. One step = every numbered item under one STEP heading; do not split a step across turns unless your output limit forces it, and then say "CONTINUING <items> NEXT TURN" and never truncate a table mid-item. Step 0 audits are read-only (grep/read/report). Never proceed to a new step without an explicit "Proceed".
3. Make the smallest change that satisfies the task. No drive-by refactors, reformatting, or dependency bumps.
4. grep/ripgrep first; read only the file regions you will edit.
5. Never modify anything under ARCHITECTURE.md "Do not touch". Never remove or alter the LICENSE file or copyright headers. Every new source file starts with `// SPDX-License-Identifier: GPL-3.0-or-later` and `// Copyright (C) 2026 Adam Hainstock (@adamjeremy-sk)`.
6. Invariants (see ARCHITECTURE.md; ask before deviating):
   - Language is C++17. GTK 4 and GLib are used through their plain C APIs; no gtkmm, no libadwaita, no language bindings, no vendor SDKs. Nothing that exists only to wrap another API: talk to the thing directly (C API, subprocess, wire protocol). A new dependency needs Adam's decision.
   - No C++ exceptions in project code (an exception escaping through a GTK callback is undefined behaviour). Return `std::optional` or a result type; use `GError` at the GTK boundary. RAII only: no raw `new`/`delete`/`g_free` outside the `gtkx` helpers.
   - Layers: `src/core`, `src/agent` and `src/ctxmon/core` never include GTK, Gdk, Pango, GtkSourceView or VTE headers (GLib, GIO and json-glib are allowed there). UI code lives in `src/ui` and `src/ctxmon/ui` only.
   - Text is UTF-8. Conversion happens only at the file boundary, with the encoding and line-ending style stated explicitly, never guessed.
   - Paths use `std::filesystem` or GIO, never string-built separators. User config, data, cache and state go to XDG locations. Nothing is written next to the executable.
   - Agent safety is a hard invariant: the agent can never change its own permission preset and can never read API keys; keys live in the system keyring and JSON holds references only; the permission presets and guards in ARCHITECTURE.md section 7.6 are not weakened without Adam's decision.
   - Every gate that adds code adds its tests. A falling test count is a defect.
7. Identity stability: never rename functions, symbols, config keys, file formats, or widget IDs when only display text changes.
8. Deletion rule: before deleting any file or symbol, grep the whole tree for every reference to it and show the raw output. One live reference from a file that stays as it is means it is NOT dead; list it as "Active - Retained". Delete in a dedicated step, never mixed with other edits. Never delete, move or clean up any file or directory the prompt does not name, including byproducts your own commands created (caches such as `__pycache__`, stray output files): list them in the report under "Unexpected files" and leave them in place; Adam decides what happens to them (Adam, 2026-11-07).
9. Concurrency: never block the GTK main loop; long work runs off the main thread; touch widgets only from the main thread.
10. If a task touches a config file format, a JSON schema, the project file, the chat archive format, the permission engine, or the agent tool-call or provider protocol, stop and propose a plan first. There is no file-count limit.
11. Verify before reporting: the project must configure, build, and pass the full test run, and a falling test count is a defect. Commands: `cmake -S . -B build`, `cmake --build build`, `ctest --test-dir build --output-on-failure`. Until gate M0.2 has created the build, say "no build yet" instead of claiming success. Adam is the build authority; report exactly what you ran.
12. Evidence: verbatim quoted code for every edit, an edited-file manifest, and grep proofs for all deletion/absence claims. In addition:
    - Every count or list shows the exact command AND its raw output in a code block (trim to 40 lines max and say how many lines were trimmed). A conclusion without its raw output is treated as unverified.
    - Raw output is pasted EXACTLY as the tool returned it. Never edit, reorder, summarize, or drop lines inside a raw-output block, never put "..." inside one, and never add lines the tool did not print. If you must trim, cut only from the end and write "[N lines trimmed]". Your output will be compared against the actual command output.
    - Every file:line comes from output that prints line numbers: `grep -n` / `grep -rn`, a `git diff` hunk header, or the IDE file tool's numbered output. NEVER give an approximate or guessed line number; if you lack one, re-run `grep -n`.
    - Proof of an edit is the raw `git diff -- <file>` output, pasted unaltered. Do not re-quote edited code by other means.
    - When a classification depends on surrounding code, quote that code (about 5 lines either side, line numbers visible). If the hit line alone proves the classification, the grep line is enough. Hits within 10 lines of each other share ONE merged range.
    - When you tabulate search results, every line of raw output appears as a table row, and any "Hits" count equals the number of raw output lines.
    - Derive every answer from a command run in the current turn. Never reuse numbers from ARCHITECTURE.md, earlier turns, or memory.
    - Never print secrets or the contents of credential files; key names only.
13. Never place secrets, API keys, build/ output, or per-user IDE state (for example .idea/workspace.xml) into git.
14. If instructions conflict with ARCHITECTURE.md, ask before deviating.
15. End every turn with: files changed + one-line why (max 10 lines), commands run + results, suggested next step, then "STOPPING AND WAITING FOR VERIFICATION" — and halt.
16. File and function size (Adam, 2026-11-05). One responsibility per file: the file's opening comment says in one sentence what it is for (the purpose comment is the line directly after the copyright line); no `utils`, `helpers`, `manager` or `common` grab-bags. A `.cpp` or `.h` over 300 lines is a review trigger: the report states why it is still one responsibility, or the task splits it. Over 500 lines: split in a dedicated step before adding anything, unless Adam approves an exception that is then noted in the file's header comment. Tests and data tables use 500 and 800. Functions over 50 lines are flagged in the report. UI: one widget or panel class per file pair; `window` only assembles panels and holds no logic (logic lives in `src/core`, where it can be tested). Every report lists `wc -l` for each file the task created or modified.
17. Fix loops, no carried debt (Adam, 2026-11-06). Every audit note is fixed before the gate is committed; nothing is carried forward as known debt. A fix arrives as a short prompt that starts with "CONTINUATION (same session)": it names the fix, the uncommitted files to expect and the evidence. Treat it exactly like a step: make only the named change, paste raw evidence, end with "STOPPING AND WAITING FOR VERIFICATION". If your context no longer holds the task the continuation refers to, say so and STOP; Adam then sends a full prompt.
18. Evidence files (Adam, 2026-11-06; from gate M0.5c1 on). Long output (build, ctest, and every proof the prompt marks FILE) is written by the command itself to `evidence/<gate>/<name>.txt` in the project root; the folder is git-ignored. Exact form: `mkdir -p evidence/<gate> && { echo "# $(date -Is) HEAD $(git rev-parse --short HEAD) :: <command>"; <command>; echo "exit=$?"; } > evidence/<gate>/<name>.txt 2>&1`. In the report, for each file paste raw the output of `tail -n 3 evidence/<gate>/<name>.txt` under its path. Re-running a command overwrites its file. Never edit or delete an evidence file by hand. Outputs the prompt does not mark FILE are pasted raw in the report as before.
19. Format before reporting (Adam, 2026-11-06; from gate M0.5c1 on). After your last edit and before the build, run `clang-format -i` on every `.cpp` and `.h` file you created or changed in this step (never on other files), so the `Format.Check` test passes. Formatting is not a drive-by edit when it touches only your own files.
20. C++ build and test traps (Adam, 2026-11-07, lessons of milestone M0). Link `vermilion_warnings` and `vermilion_noexc` PRIVATE, never PUBLIC: a PUBLIC link passes `-fno-exceptions` on to every target that links the library, the tests included. Regular expressions use GLib's `GRegex` (`g_regex_new`, `g_regex_match`, `GMatchInfo`); never `std::regex`, which reports errors by throwing and has no lookbehind. In GoogleTest, compare C strings with `EXPECT_STREQ` or as `std::string`; `EXPECT_EQ` on two `const char*` compares pointers.
21. No checks that write files (Adam, 2026-11-08). Verify with the build, the tests and the commands the prompt lists; never run a compiler, linter or script on your own initiative if it can write files as a side effect (for example `python3 -m py_compile`, which leaves `__pycache__/`). If a command you were told to run leaves unexpected files, rule 8 applies: report them under "Unexpected files" and leave them in place.
### TOOLING & FILESYSTEM RULES (CRITICAL)
- **Harness precedence**: you run as OpenCode, an ACP agent hosted by the Air plugin inside CLion, talking to a local llama.cpp server (details in HANDOFF.md section 2b). Where this file and the harness's own tool instructions disagree on HOW to read, search or edit files (which tool, absolute vs relative paths), follow the harness. This file governs WHAT you may change, the gate protocol, and what evidence you report. Do not deliberate over this; pick the harness way and proceed.
- **Paths**: the project root is the open CLion project. Shell commands run from the project root with relative paths. Never read or write outside the project root.
- **Shell**: use whatever the task needs (opt-out policy, Adam 2026-11-05). Prefer the built-in file tools for reading and editing files, and `grep`/`git` for evidence. The one exclusion: you never commit and never push. Adam does both.
- **Approvals and protected config** (opt-out policy, set by Adam on 2026-11-05, destructive git added the same day): file edits and shell commands run without a prompt, except the git commands `opencode.json` denies: `commit`, `push`, and the ones that create commits (`cherry-pick`, `merge`, `rebase`, `revert`, `am`); and the ones that discard or move work (`checkout` in every form, `switch`, `restore`, `reset`, `clean`, `stash`, `update-ref`). Each is denied with and without global options (`git -C dir <cmd>`, `git -c k=v <cmd>`). Never commit, push, or discard work by any other route either; Adam commits and pushes when a gate is finished. Web access is denied. Never edit, delete, or work around `opencode.json` or anything under `~/.jetbrains/`; if a permission blocks you, say so and STOP. Freedom does not relax anything else: one step per turn, rule 8 deletion proof, and the "Do not touch" list still apply.
- Do not write temporary or scratch files (no `/tmp`, no files in the repo). Use pipes. The one exception is `evidence/` (rule 18).
- **Tool-call budget**: at most 10 commands per tool call (chained with `&&` counts each command). Never run a command whose exact text you have already run in this turn. Never request overlapping line ranges; merge them.
- **Loop guard**: if you notice you are emitting the same command, line, or phrase repeatedly, stop immediately, write "LOOP DETECTED" with the last distinct thing you were doing, and STOP. A short honest stop is always better than a long repeated one.
### CONTEXT RESETS (CRITICAL)
Your context is frequently wiped mid-task. These rules exist so a wipe never causes damage:
- On every fresh context, re-read this file before doing anything else. These rules are standing; they apply even if the current prompt does not repeat them.
- Never assume the result of a previous step or turn. If the prompt does not state the last verified state, run `git status --short` and `git log --oneline -3`, report them, and ask which step to resume. Do not continue a task from memory.
- Adam commits only when a whole task is finished, so earlier passed steps are often uncommitted. The prompt's "Last verified" line lists the files expected to be modified. Build on those. If `git status --short` shows any change to a file NOT on that list, do not modify, revert, or build on it: report it and STOP. Never run `git restore`, `git checkout` (any form), `git switch`, `git stash`, `git reset` or `git clean`; `opencode.json` denies them too.
