- 2026-11-17 — (Adam, M2.4 design talk, topic 4; the hash is Adam's idea) **Our own saves are told from outside changes by the file's modification time and size, and then by a hash of the file's bytes.** Each document records time, size and hash after every load, reload and own save. A monitor event whose time and size match the record is ignored without reading. If they differ, the file is read and hashed (off the main loop, on GIO's thread pool): an equal hash means nothing really changed (a `touch`, a formatter rewriting identical text), so only the recorded time is updated, with no reload and no banner; a different hash is an outside modification (a silent reload for a clean buffer, the banner for a dirty one). The first hash comes from the scanner's existing whole-file pass on open; after our own save the file is read back once. "Keep mine" (topic 2) records the disk's new time, size and hash. All behind one function, `hash_file`. Known limits: a tool that rewrites a file with the same size and restores the old time is missed by the fast path; an outside change between our save and the read-back would be recorded as ours (tiny window). Declined: time and size only, a compare of the file with the buffer text (encodings and line endings make it awkward), ignoring events for a moment after a save (can hide a real change).
