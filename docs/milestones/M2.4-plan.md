# M2.4 plan: the file monitor and the external-change policy

Status: DRAFT of 2026-11-17 (twelfth chat), for Adam's review. The decisions behind it are in HANDOFF.md, Active-gate decisions (the M2.4 design talk, topics 1 to 8). This file adds what the design talk did not settle: what the code looks like, the order of the steps, and three open points (section 6). Qwen writes the implementations; the Orchestrator dictates headers and tests (AI_ONBOARDING.md 2.8).

## 1. What the gate delivers

- A clean tab whose file changes on disk reloads by itself (10 MB or less), the undo history cleared, cursor and scroll kept, the status bar saying "Reloaded <name> (changed on disk)". A clean tab over 10 MB, and every tab with unsaved changes, shows a banner (Reload, Keep mine; Reload, Ignore over 10 MB for a clean tab). Show diff joins the banner at M2.6.
- A deleted or moved file keeps its tab, the text and an unsaved mark; the file coming back reloads it (clean) or shows the banner (edited).
- Our own saves, a `touch` and a formatter that rewrites identical text never show anything: time and size first, then an xxHash of the bytes.
- Only the active tab is watched; a background tab is checked when it is selected; every tab is checked at quit (and a single tab when its close button is pressed).
- File > Reload from Disk, Ctrl+R, with the large-file confirmation and its "Do not ask again" preference.
- A small settings-file module (`settings.ini`, one key) and the vendored xxHash.

## 2. Facts the plan stands on

**What the monitor reports (probe, 2026-11-17, GLib 2.80.0, inotify; run in the Orchestrator's workspace, not on Adam's machine).** For a file watched by path:

| Change | Events |
|---|---|
| append, or truncate and write | CHANGED, CHANGES_DONE_HINT |
| `touch` (time only), `chmod` | ATTRIBUTE_CHANGED only |
| write a temp file and rename over (git, gedit, our own save through GIO) | DELETED of the temp name, CREATED and CHANGES_DONE_HINT of the watched name; no DELETED for the watched name |
| delete | DELETED |
| delete, then recreate | CREATED, CHANGED, CHANGES_DONE_HINT |
| move away | DELETED of the watched name (with `WATCH_MOVES`: RENAMED); moving back: CREATED and CHANGES_DONE_HINT |

Consequence, and the rule of the design: **an event only means "look at the file again".** The code never decides from the event kind; after the 300 ms debounce it reads the file's state (exists, time, size) and decides from that. `WATCH_MOVES` is not used. This is also why the probe need not be repeated on Adam's machine. The monitor keeps working after a delete and a recreate.

**What the code does today (read 2026-11-17).**
- `DocumentSaver` maps `overwrite_changes` to `GTK_SOURCE_FILE_SAVER_FLAGS_IGNORE_MODIFICATION_TIME`; otherwise GtkSourceView compares the file's time with the one it recorded at the last load or save and raises `EXTERNALLY_MODIFIED`. That recorded time cannot be set from outside. So after "Keep mine", or after a `touch` that the hash showed to be harmless, GtkSourceView would still ask Save Anyway. **The plan therefore moves the check into our own code for every file document:** the save always passes the ignore flag and the page checks the file against the document's own baseline first.
- That machinery already exists for recovered documents only: `RecoveredBase` (path, time), `needs_base_check()`, `file_changed_since_base()` in `src/core/recovered_base.*`, used by `EditorPage::save()` with `expect_file_time()`. M2.4 generalises it: the baseline (time, size, hash) is recorded for every file document, and `RecoveredBase` is replaced by it in its own step with its tests carried over.
- `DocumentObserver::document_synced(id, mtime)` already reports the file's time after every load and save; it grows a size, and the hash follows.
- `FileProbe` + `TextScanner` already read a whole file once before an open. The scanner gets the hash; a reload goes through the same probe and loader as an open, so a reload scans the new content (NUL, long line) as decided in topic 6.
- `DebounceTimer` (`GlibTimer` in the program, a fake in tests) exists and is reused. There is no banner widget yet, no `third_party/` folder and no settings code.

## 3. Shape of the code

New in `src/core` (no GTK; GLib allowed):
- `file_hash.{h,cpp}`: `StreamHasher` (XXH3 64-bit, update in blocks, digest) and `hash_file_blocking(path)` (64 KiB reads, returns size and hash or an error). Only this `.cpp` includes the vendored header (`XXH_INLINE_ALL`, as a system header).
- `file_stamp.h`: `FileStamp { mtime_us; size; hash (optional) }`, the document's baseline, and `DiskState { exists; mtime_us; size }`, what a look at the file returns.
- `external_change.{h,cpp}`: the decision as pure functions, so the whole policy is tested without a display. `needs_hash(stamp, disk)` (time or size differ), then `decide(stamp, disk, hash, document)` returning one action: Ignore, UpdateStampOnly, ReloadSilently, ShowBanner (with the kind: Changed, ChangedLarge), MarkDeleted, FileReturned. The inputs are clean or edited, read-only, deleted flag, size against the 10 MB constant (`kLargeFileBytes` = 10,485,760), and whether a reload would trigger an open-time question.
- `external_messages.{h,cpp}`: every text (status line, banner text, quit-question extra line), like `save_messages`.
- `settings_file.{h,cpp}` and `settings_keys.h`: see 3a.
- `text_scan` gains `ScanResult::hash`.
- `DocumentList` gains `deleted_on_disk` in the record (with `needs_save()` = modified or deleted) and its setter.

New in `src/ui`:
- `file_checker.{h,cpp}`: looks at a path off the main loop (GIO thread pool): state, and the hash when asked. A thin wrapper over the core functions.
- `file_watcher.{h,cpp}`: one `GFileMonitor` on the active tab's path plus a `DebounceTimer` (300 ms); the callback says "look again".
- `change_banner.{h,cpp}`: the banner (a plain box with a label and text buttons, styled by one CSS class; GtkInfoBar is not used because it is deprecated in GTK 4). It sits above the view inside the page, which means the page's widget becomes a box holding the banner and the scrolled view (`EditorPage::widget()` keeps its meaning).
- `external_change_controller.{h,cpp}`: owns the watcher, runs the checks (monitor event, tab switch, quit, single-tab close), applies the actions, holds the one reload routine behind the menu item and the banner button.
- A question with a "Do not ask again" check box (a variant next to `ask()` in `close_dialog`).

Rules for timing (they close the holes found while planning):
- While a page loads, saves, is locked by Replace All, or is **syncing** (from the end of a save until its baseline is recorded: the time and size read, then the hash read back), checks for that page wait and run when it is idle again. Otherwise our own save would look like an outside change.
- A check that finds time and size equal to the baseline ends there, without reading the file.
- The hash is read on the thread pool; the result is dropped if the document changed or closed meanwhile (`AsyncGuard`).
- Network drives send no events: they are caught at a tab switch and at quit, as decided.

### 3a. The settings file (the part that needs your approval, rule 10)

- Path `$XDG_CONFIG_HOME/vermilion/settings.ini` (fixed in ARCHITECTURE.md section 8), a `GKeyFile`. The folder is created if missing.
- Group `[files]`, key `confirm-large-reload`, boolean, default `true`. The name is permanent once written.
- Loading keeps comments and every key it does not know. Saving loads the file again, sets the known keys and writes it through a temporary file and a rename, so the light editor and the IDE can both write without overwriting each other's keys.
- A missing file gives the defaults and is not created until a setting is changed.
- A file that cannot be parsed: see open point 1.
- The module offers typed reads and writes (`bool` now; the M2.5 window adds the others) and knows nothing about GTK.

## 4. Steps (one prompt each; the Orchestrator audits each before the next)

**M2.4a: the hash and the settings file** (infrastructure, no visible change)
1. **Vendor xxHash (Adam's part, no Qwen).** `third_party/xxhash/xxhash.h` and `LICENSE` from the v0.8.3 release (Adam downloads and copies them; the Orchestrator never retypes them), byte-exact. The Orchestrator records the version and both sha256 sums with `device_bash`. The release's `LICENSE` file holds the BSD-2 text of the library and the GPLv2 text of the `xxhsum` tool; only `xxhash.h` is used, and a one-line `third_party/xxhash/README.md` says so. `check_sources.sh` and `check_format.sh` do not scan `third_party/`.
2. `file_hash` with `StreamHasher`, `hash_file_blocking`, the CMake line that marks the folder as a system include, and tests (the empty input, streaming equals one-shot for every split of a sample, a missing file, a directory, a file larger than one block).
3. The scanner's hash: `ScanResult::hash`, tests that it is independent of how the blocks are split and equals `hash_file_blocking` on the same bytes.
4. `settings_file` and `settings_keys` with tests (missing file, round trip, unknown keys and comments kept, wrong value type gives the default, a damaged file, the temporary-file write leaves nothing behind, two writers).

**M2.4b: the policy and the wiring**
5. The core policy: `file_stamp.h`, `external_change`, `external_messages`, `kLargeFileBytes`, with table tests for every topic (1 to 7) including the read-only and open-time-question cases. Largest test file of the gate; split in two if it passes 500 lines.
6. The baseline replaces `RecoveredBase`: `DocumentList` gets the deleted flag, `EditorPage` keeps a `FileStamp` for every file document, the save always passes the ignore flag and checks the baseline first, `document_synced` carries the size, the hash is read back after an own save, "Keep mine" and "equal hash" update the baseline. The recovery tests are carried over unchanged in meaning. The recovery tracker treats a deleted document as unsaved (it gets a copy; the copy is deleted when the file returns).
7. `file_checker` and `file_watcher`, plus the banner widget and its CSS class (the banner can be shown by a test hook in the window before the policy drives it).
8. The reload routine (probe, load, undo cleared, cursor and scroll kept, encoding rule of topic 6, status line) and the controller that applies the actions: monitor events, tab switch, deleted and returned.
9. Quit and single-tab close checks (the extra line in the quit question, the deleted tab asking Save / Close Without Saving), through `SaveController`.
10. File > Reload from Disk (Ctrl+R): the action and its greying, the confirmations, the check box and the setting; the settings file is loaded at start-up in `main_window` and written when the box is ticked.
11. Adam's hands-on list (a script of edits made from a terminal: append, rewrite identical text, touch, git-style rename-over, delete and recreate, move away and back, 10 MB and 50 MB files, two tabs, quit with a changed file), then the final build, the full test run and the docs sweep (manual topic "Files changed on disk", `Ctrl+R` in the shortcut lists, ARCHITECTURE.md sections 6, 7.6, 7.1 and 9, roadmap, README, the M9 NOTICE entry). Steps 5 to 10 may be split further when a prompt would pass about 40 KB.

Progress bar: if M2.4 is split into M2.4a and M2.4b in the roadmap, only M2's own fraction changes (HANDOFF.md, topic 7). Orchestrator's suggestion: keep it one gate, M2.4, with eleven steps, because the two halves are not useful alone and the bar stays honest.

## 5. Risks

- Step 6 touches tested code (saving, recovery). Mitigation: the recovered-document cases of the old tests stay and must still pass; the audit reads the save path line by line.
- The page's widget becomes a box (step 7); everything that finds the view through the page must keep working (search, the Replace All lock, the lock keys). Audit with a grep for `widget()` users.
- Dialog with a check box (step 10) is new UI; nothing like it exists in `close_dialog`.
- The hash after our own save is a second whole-file read (a 38.9 MB save already takes 6.5 s; the read adds well under a second on the thread pool).

## 6. Open points for Adam

1. **A damaged `settings.ini`.** Recommendation: use the defaults for the run and show one status line; do not touch the file until a setting is changed, then move the damaged file to `settings.ini.bad` and write a fresh one. The other option is never to overwrite a file we cannot read and to keep the setting in memory only.
2. **A recovered document after a restart.** It knows its file's old time but not its size or hash. Your earlier default (the Orchestrator's proposal, not discussed) was that, once the recovery question is answered, the document takes the file's current state as its baseline. That would drop today's rule that the first save asks Save Anyway when the file changed since the copy, which M2.2c built and tested. Recommendation instead: keep that rule; the first check treats a time that differs from the copy's as "the file changed since the copy" and shows the banner (the document has unsaved changes, so it is a banner case anyway), and fills in size and hash only when the time matches.
3. **xxHash v0.8.3** (the maintenance release of December 2024; Ubuntu 24.04 carries 0.8.2) as the pinned version, and the license handling above.
