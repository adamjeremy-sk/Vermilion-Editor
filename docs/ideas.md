# ideas.md: Potential features (unscheduled)
**Purpose**: a parking place for ideas as they come. Nothing here is planned, scheduled or promised.
**Rule (Adam, 2026-11-10)**: the roadmap does not grow until version 1.0.0-stable is reached; only then are other features considered. Only Adam moves an idea from this list into `docs/roadmap.md`.
Features that were decided against earlier are listed under "Dropped" in ARCHITECTURE.md section 2; they come back here only if Adam brings one back.

| Idea | Added | Notes |
|---|---|---|
| Vi / Vim key bindings (optional, switched on in settings) | 2026-11-10 | GtkSourceView 5 appears to provide a Vim input method (`GtkSourceVimIMContext`); to be confirmed against version 5.12 before any promise. |
| Emacs key bindings (optional) | 2026-11-10 | No ready-made support in GtkSourceView or GTK 4; it would be our own key handling, so a larger job than Vim keys. |
| Tab limit (optional): when more than N tabs are open (for example 20), the least recently used one closes, never one with unsaved changes, with a status bar message | 2026-11-10 | Planned for the old M2.6 (now M2.7), dropped by Adam before M2.1: Vermilion does not close tabs on the user. It would need a recent-use counter in `DocumentList`. |
| Action chains (working name; also considered: Chord line, Quick verbs): a colon opens a one-line entry, then a string of letters runs actions in order when Enter is pressed. Example: `:wdb` + Enter would write the file, build, then debug | 2026-11-11 | Adam's idea. Each letter maps to a `GAction`, so the action table already exists. Open points for when it is considered: a colon is an ordinary character in a text editor, so it needs its own trigger (a shortcut, or Esc then colon) because Vermilion is not modal; a chain should stop at the first action that fails (a failed build must not start the debugger); the letter map fixed or user-defined; how it relates to Vim's `:` command line if Vim keys are ever added. Needs Build (M4) and Debug (M7) to be worth much. |
| Edit journal for crash recovery: instead of copying the whole document, append each edit (what was inserted or deleted, and where) to a small log in the background; recovery replays the log on the original file | 2026-11-11 | From the M2.2c talk (option E). Cost per keystroke does not depend on file size, so it suits huge files, but it is a new file format and replay must be exact. Considered only if the copy-based recovery of M2.2c (with its back-off and sliced copy) proves too slow on very large documents. |
| Native Anthropic Messages adapter | 2026-11-13 | Parked by Adam: the agent is local first (llama.cpp through the OpenAI-compatible API). Was gate M8.3. The provider interface of M5.1 is the seam; the adapter would need the same recorded-stream tests as the OpenAI-compatible one. |
| Native Gemini adapter (Gemini already works through Google's OpenAI-compatible endpoint) | 2026-11-13 | Parked by Adam. Was gate M8.4. Build only if the compatible endpoint lacks something needed. |
| MCP server (stdio): expose Vermilion's tool registry to other agents | 2026-11-13 | Parked by Adam. Was gate M8.7. The built-in agent calls its registry in process, so this only serves outside agents. The registry's shape (name, JSON schema, function) is the MCP shape, so it needs no redesign. Reconsider after DOGFOOD 4 (Adam, 2026-11-14) if outside agents such as OpenCode should use Vermilion's buffers and editor state: a stdio server is started by the outside agent as its own process, so it would need a link (for example a Unix socket) into the running editor, which makes it more than a thin adapter. |
| MCP client (stdio): let the agent call outside tool servers | 2026-11-13 | Parked by Adam. Was gate M8.8. Expansion, not a requirement for a working agent. |
| Key storage in the system keyring (libsecret) | 2026-11-13 | Parked by Adam (the keyring half of M5.6). Keys are `env:NAME` references until then; the key resolver answers `keyring:` with "not supported in this version", so adding it changes no format. Costs: a running keyring service (GNOME Keyring or KWallet; XFCE may have none), async calls, a fake for tests, a "store key" field in the setup dialog. Only matters for remote endpoints. |
| Context summarising: at about 80% of the context, older turns are summarised | 2026-11-13 | Parked by Adam (was gate M5.12). Until then the loop stops cleanly with "context full, use /clear" (M5.4). |
| Histogram diff (and patience diff) as an alternative to Myers | 2026-11-13 | Adam's idea. They anchor on lines that occur once and give nicer results on code with repeated lines such as `}`. The diff engine (M2.6) keeps the algorithm behind one function so it can be swapped. |
| Change sets, the heavy parts: persisted change sets (revert after a restart), one undo step per agent turn | 2026-11-13 | Parked by Adam; M5.6 is the lean version (in-memory change sets, snapshots, whole-turn revert). Per-hunk Accept and Revert was part of this row and came back into M5 on 2026-11-14 (M5.6b and M5.11b). Grouped undo needs GtkSourceView's user-action grouping held open across an asynchronous turn while the user may also type. |
| `.rpm` packages, built and tested in a Fedora virtual machine | 2026-11-13 | Parked by Adam. The `.deb` packages and the release zip with `install.sh` cover M9. Open points were the dependency names and the Fedora release. |
| `replace_lines` and `insert_at_line` agent tools | 2026-11-14 | Deferred by agreement with Adam: built only if exact-match `replace_text` fails often (the OpenCode usage log, DOGFOOD 4). OpenCode hides its patch tool from non-GPT models, so simple edit shapes may suit a local model better anyway. |
| Whitespace tolerance for `replace_text` (several matching strategies from strict to loose) | 2026-11-14 | Gap 1 of the OpenCode comparison, marked at Adam's request. A third-party guide says OpenCode's `edit` does this (not confirmed in the official docs); Adam's view is that Qwen simply handles exact match well. Decided in the M5.3b plan from evidence. |
| `todo` list tool for multi-step agent tasks | 2026-11-14 | OpenCode has one. Needs a chat widget, and small models can loop on todo lists; left out of the thirteen-tool v1 set. |
| Read-only plan mode (a permission preset with edits and shell off) | 2026-11-14 | OpenCode has a read-only planning agent. Cheap to add once the preset table exists. |
| Problems reported automatically after each agent edit | 2026-11-14 | OpenCode runs its language-server diagnostics after each write (from a third-party guide). Vermilion has no language server, so it would mean running the problem matchers on a build; today the agent gets problems from `run_build`. |
| Symbol outline and go-to-definition tools for the agent | 2026-11-14 | Needs a language server or ctags, a separate decision and probably a new dependency. |
